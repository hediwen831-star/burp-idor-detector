# 设计文档：越权检测的判定模型

> 这份文档讲「为什么这么设计」，README 讲「怎么用」。
> 关于「这个判定准不准、为什么」的答案都在这里。

---

## 一、问题的定义

越权访问（IDOR）的形式化描述：

```
正常流程：
    身份 A  ──请求 id=X──▶  服务端  ──校验 A 是否拥有 X──▶  返回 X 的内容

越权：
    身份 B  ──请求 id=X──▶  服务端  ──【没有校验】──▶  返回 X 的内容
                                       ↑
                                  漏洞就在这一步缺失
```

检测的目标就是：**判断服务端有没有做那个校验。**

我们无法直接看到服务端的代码，只能通过行为推断：

```
如果 服务端在「身份 B 请求 id=X」时返回了 X 的内容
    → 说明它没有校验 B 是否拥有 X
    → 越权成立
```

听起来很直接，但有两类干扰需要排除，这就是下面两节的来历。

---

## 二、干扰一：公开资源（为什么要第三个请求）

「身份 B 拿到了 X 的内容」**不等于**越权。

反例：商品详情页。

```
身份 A  ──请求 id=1001──▶  返回商品详情
身份 B  ──请求 id=1001──▶  返回同样的商品详情     ← 这是正常的！
```

因为商品信息本来就是公开的，谁来看都一样。

**所以「换身份后响应相似」这个判据本身是不充分的。**

### 引入对照请求

关键洞察：如果 `id=1001` 真的是「身份 A 的私有资源」，
那么 `id=1001` 与 `id=不存在` 的响应**应该有本质区别**。

于是加一个请求：

```
① 身份 A，id=1001        → R0   基准
② 身份 B，id=1001        → R1   换身份
③ 身份 B，id=999999999   → R2   对照（几乎不可能存在的 ID）
```

判定表：

| R1 vs R0 | R2 vs R0 | 结论 | 理由 |
|---|---|---|---|
| 相似 | **不相似** | **越权** | B 拿到了和 A 一样的数据，且该 ID 确实指向真实存在的资源 |
| 相似 | **相似** | 误报 | 这个接口对任何 ID 都返回固定内容，前一步的「相似」没有意义 |
| 不相似 | 任意 | 权限校验有效 | B 被正确拦截 |

**第 2 行是这个设计的价值所在** —— 它把「通配响应」这类假阳性在判定阶段就挡掉了。

> 这个思路和 [ASP 攻击面平台](https://github.com/hediwen831-star/attack-surface)
> 里的「负向对照校验」是同一件事：
> **排除「检测特征被检测行为本身制造出来」的可能。**
>
> 在 ASP 里是「命中之后向随机路径再发一次请求」；
> 在这里是「用一个不存在的 ID 再发一次请求」。

## 三、干扰二：动态内容（为什么不能直接比字符串）

即使两次请求返回的是**同一份数据**，正文也几乎不可能逐字节相同：

| 动态内容 | 变化原因 |
|---|---|
| CSRF token | 每次请求服务端重新生成 |
| 会话标识 | 同上 |
| 时间戳 / 耗时 | 天然不同 |
| traceId / requestId | 分布式追踪要求唯一 |
| 长十六进制串 | 哈希、随机 ID |

**如果直接做字符串相等判断**：

```
R0 与 R1 必然不同 → 判定为「不相似」 → 所有越权被漏掉
```

**如果为了迁就动态内容而放宽判据**（比如只看长度）：

```
两个不同的错误页（长度接近）→ 判定为「相似」→ 大量误报
```

所以必须做**两步**：

### 第一步：标准化

把动态内容替换成占位符：

```
{"csrfToken":"aaa111","traceId":"4bf92f3577b34da6..."}
              ↓ 标准化
{"csrfToken":"<DYNAMIC>","traceId":"<DYNAMIC>"}
```

标准化之后，只有**业务数据**参与了后续比较 —— 这正是我们想要的。

### 第二步：结构化比较

标准化后的正文用 **5-gram 集合的 Jaccard 相似度** 比较，再与状态码、Content-Type 加权组合：

| 维度 | 权重 | 理由 |
|---|---|---|
| 状态码 | 0.3 | 302 和 200 即使正文都为空，语义也完全不同 |
| Content-Type | 0.1 | JSON 和 HTML 是两种完全不同的响应 |
| 正文 5-gram Jaccard | 0.6 | 主要依据 |

**为什么给状态码这么高权重**：

```
权限校验有效的典型表现是：
    身份 B 请求 → 302 跳转到登录页（或 403）
    响应正文可能很短、甚至是空的

如果只看正文，这个响应和「一个空的正常响应」很难区分。
但状态码明确告诉了我们：**权限校验起作用了。**
```

**为什么用 5-gram 集合而不是直接比文本**：

集合对「局部插入/删除」不敏感 —— 一次请求多返回一个字段，
不该让相似度崩掉。而这是真实场景里的常态。

## 四、参数识别：为什么用启发式

越权检测的第一步是「找到值得换身份重放的那个参数」。
这一步的准确率直接决定后面会不会满屏误报。

### 为什么不让用户配清单

参数命名没有标准：

```
id / uid / userId / user_id / memberId / account / no / code / sn / ...
```

让用户逐个填不现实，而**漏填就意味着漏检**。

### 双维度判定

| 维度 | 检查内容 |
|---|---|
| **参数名** | 命中 ID 关键词表，或匹配 `*_id` / `*Id` / `*_no` / `*Code` 模式 |
| **参数值** | 形态像标识符：纯数字 / UUID / 短 token |
| **排除表** | 分页、排序、时间戳、版本号、鉴权 token —— 这些换身份重放没有意义 |

三个维度都满足才判定为候选。

### 为什么「值形态」也要参与判断

反例：`status=1`、`type=2`、`level=3`。

这些参数名可能命中 ID 模式（如果写到排除表之外），
值也是数字，看起来完全像 ID。但它们的值是**枚举**，不是资源标识 ——
换个身份重放没有意义，只会产生误报。

所以加了值形态判断，并且**排除了「短纯字母」**（如 `status=active`）。

### 取舍方向与 ASP 项目相反

| | ASP（攻击面） | 本插件（越权） |
|---|---|---|
| 取向 | **宁可多留**，不漏掉真实资产 | **宁可少报**，不产生无效请求 |
| 原因 | 漏报没法补救（资产下线就找不回来了） | 误报意味着**对目标发起无意义的额外流量** |

**同样的「误报 vs 漏报」问题，因为代价不同，取舍方向就不同。**
这是设计里值得注意的一点 —— 没有普适的最优解，只有针对具体场景的权衡。

## 五、安全默认值：为什么默认不发请求

一个插件如果在后台**自动**对每个看起来像 ID 的参数发起额外请求：

| 风险 | 具体后果 |
|---|---|
| **把目标打挂** | 一个列表页可能有几十个 ID 参数 ×（重放 + 对照）= 流量放大数倍 |
| **污染业务数据** | 如果检测到写接口，重放可能真的修改了数据 |
| **打草惊蛇** | 授权测试有明确窗口期，插件擅自发请求属于越界 |

**所以 `activeReplayEnabled` 默认是 `false`。**
插件装上后只做被动观察（识别候选、记录日志），不发任何请求。

用户必须显式做两件事才会开始检测：
1. 配置第二身份
2. 勾选「启用主动重放」并保存

### 即使打开了，还有四道限制

| 限制 | 值 | 目的 |
|---|---|---|
| 方法白名单 | 仅 GET / HEAD / OPTIONS | 避免误改业务数据 |
| 限速 | 默认 100ms 间隔 | 不让插件变成压测工具 |
| 单 host 配额 | 默认 50 个候选 | 防止在中大型站点上刷出成百上千请求 |
| 范围控制 | 可指定只检测/排除的 host | 让用户能精确控制流量去向 |

**为什么 POST 也排除**：POST 可能是查询（GraphQL、搜索接口都是 POST），
但它同样可能是「提交订单」。在无法区分的情况下，**保守的做法是不碰**。

如果确实需要测 POST 接口，应该由用户在明确知道接口语义的前提下
手动用 Repeater 验证 —— 而不是让插件自动扫描。

> 这与 ASP 项目里「Web 接口默认只绑 127.0.0.1、绑公网必须配 token」
> 是同一类取舍：**工具的能力边界就是它的风险边界，默认值必须选安全的那一侧。**

## 六、明确不做的事

诚实地列出边界，比假装全能更可信：

| 不做 | 原因 |
|---|---|
| **写接口的越权检测** | 重放可能真的改数据，风险不可接受（见上一节） |
| **自动遍历 ID 空间** | 会产生大量请求。真实渗透里这一步应该由人工在明确目标后手动做，而且要控制节奏 |
| **判断业务语义** | 「该资源本就对第二身份开放」这类判断需要业务知识，自动化做不到。所以结果只是「疑似」 |
| **GraphQL 嵌套查询** | 参数在 query body 的嵌套结构里，当前的 URL/表单参数解析覆盖不到 |
| **解析 JWT 内部结构** | 只把它当成一个请求头的值，不解析 claim。越权判断不需要知道 token 里有什么 |
| **自动上报漏洞** | 结果只进 Burp 的 Issue 列表，不自动提交到任何平台 |

## 七、与同类工具的差异

| 工具 | 交互模型 | 是否有对照请求 |
|---|---|---|
| Autorize | 手动配置 → 拦截流量 → 人工逐条查看 | ✗ |
| AuthMatrix | 手动定义角色 × 请求矩阵 | ✗ |
| Authz | 手动配置 + 对比 | ✗ |
| **本插件** | **自动挑候选 + 自动判定** | **✓** |

**真正的差异点是第 ③ 步对照请求。**

Autorize 这类工具的一个已知痛点是误报：遇到「任何 ID 都返回固定内容」的接口时
会报出大量假阳性，用户需要人工排除。

本插件用「不存在的 ID」做负向对照，把这类误报在判定阶段就挡掉。

**这不是「首创」** —— 对照实验是安全测试里的通用方法。
只是同类 Burp 插件里较少把这一步做成自动化的默认行为。

---

## 八、可以继续做的方向

按价值排序：

1. **WebSocket / GraphQL 支持** —— 现代应用越来越多地用它们承载业务数据
2. **参数值自动变形** —— 当前只做「换身份」，可以扩展成「换 ID 值」（同身份的横向越权）
3. **结果导出为可复现的验证脚本** —— 把命中项导出成一键重放的 Python/curl 脚本，
   方便在报告里附证据
4. **与 CI 集成** —— 让 Burp 的 Issue 结果可以被流水线消费
5. **JMX / 序列化参数的支持** —— 目前只解析 URL query 与表单 body
